## 1. What MuJoCo is

MuJoCo (Multi-Joint dynamics with Contact) is a rigid-body physics engine from
Google DeepMind. You describe a scene in an XML dialect called **MJCF**, and
MuJoCo integrates the equations of motion forward in time, resolving contacts
as it goes.

**The one idea to hold onto** — there are two objects, and keeping them straight
makes everything else easy:

| | `mjModel` | `mjData` |
|---|---|---|
| holds | what is **constant** | what **changes** |
| examples | masses, geom sizes, friction, gravity, timestep | positions, velocities, forces, contacts, the clock |
| comes from | compiling your XML | `MjData(model)` |
| in Python | `model = mujoco.MjModel.from_xml_path(...)` | `data = mujoco.MjData(model)` |

`mujoco.mj_step(model, data)` reads the model, and advances the data by one
timestep. The model is not modified by stepping. That separation is why one
model can back many independent `mjData` instances — useful later for running
many rollouts at once.

So the whole simulation is three lines plus a loop:

```python
model = mujoco.MjModel.from_xml_path("scenes/01_ball_drop.xml")
data  = mujoco.MjData(model)
while data.time < 5.0:
    mujoco.mj_step(model, data)
```

Everything else in this project is scaffolding around those four lines.

## 2. Install

This project uses [`uv`](https://docs.astral.sh/uv/) for its Python environment,
which keeps MuJoCo isolated from the `anaconda3` base env where your
`build123d`/`cadquery` CAD work lives.

```bash
cd "04 - Simulation"
uv sync                 # creates .venv and installs from uv.lock
```

That is the whole install. Then prefix commands with `uv run`:

```bash
uv run python scripts/run.py scenes/01_ball_drop.xml
```

`uv run` activates the environment for that one command, so there is no
`source activate` step to forget.

**No `apt install` is needed on this machine.** MuJoCo needs an OpenGL backend,
and all three it can use are already present here (`libEGL.so.1`,
`libOSMesa.so.8`, `libglfw.so.3`), as is WSLg for on-screen windows. If you ever
move this to a bare Linux box or a container, that is when you would need:

```bash
sudo apt install libgl1 libegl1 libosmesa6 libglfw3   # only if missing
```

## 4. Anatomy of an MJCF file

Here is `01_ball_drop.xml` with the comments stripped out, so the structure is
visible at a glance:

```xml
<mujoco model="ball_drop">
  <option timestep="0.002" gravity="0 0 -9.81" integrator="Euler"/>

  <asset>
    <texture name="grid" type="2d" builtin="checker" .../>
    <material name="grid_mat" texture="grid" .../>
  </asset>

  <worldbody>
    <light pos="0 0 3" dir="0 0 -1"/>
    <geom name="floor" type="plane" size="10 10 0.1" material="grid_mat"/>

    <body name="ball" pos="0 0 2">
      <freejoint/>
      <geom name="ball_geom" type="sphere" size="0.15" rgba="0.9 0.3 0.2 1"/>
    </body>
  </worldbody>
</mujoco>
```

### `<option>` — global physics

- **`timestep`** — seconds of sim time per `mj_step`. `0.002` (500 Hz) is the
  default. Smaller is more accurate and more stable but costs more CPU.
  **If anything jitters, sinks, or explodes, halve this first.**
- **`gravity`** — a 3-vector in m/s², not a scalar, so you can tilt it or zero
  it. Earth `0 0 -9.81`; Moon `0 0 -1.62`; Mars `0 0 -3.72`.
- **`integrator`** — `Euler` (default) is fine for contact-heavy scenes. `RK4`
  is more accurate for smooth dynamics; `implicitfast` helps with strong
  damping. Only reach for these after a smaller timestep has failed. See §9.1
  for how they differ.

### `<asset>` — nothing physical

Textures, materials, meshes. Purely visual, except that a `<mesh>` here can
then be referenced by a geom and so become collidable.

### `<worldbody>` — the scene tree

`<worldbody>` *is* the static world. The single most important structural rule:

> A `<body>` moves only if it has a joint. A geom placed directly in
> `<worldbody>`, or in a `<body>` with no joint, is **immovable** — regardless
> of its mass.

That is how you build floors, walls and fixtures: just leave the joint out.

### `<freejoint/>` — what makes something dynamic

`<freejoint/>` grants all 6 rigid-body degrees of freedom (3 translation +
3 rotation). It is what lets gravity and contacts move a body.

**Comment it out of `01_ball_drop.xml` and re-run.** The ball hangs in mid-air,
perfectly still. Nothing is wrong with gravity — the body simply has no DOFs to
move along. *"My object won't move"* almost always means a missing `freejoint`.

This is also where `nq` and `nv` come from. One freejoint adds:

```
nq += 7     qpos = [x, y, z, qw, qx, qy, qz]      position + quaternion
nv += 6     qvel = [vx, vy, vz, wx, wy, wz]       linear + angular velocity
```

Seven position numbers but six velocities, because a unit quaternion has four
components encoding only three rotational DOFs.

### `<geom>` — shape, collision and appearance

**Size is always a radius or half-extent, never a full width.** A box with
`size="0.1 0.1 0.1"` is 0.2 m on a side. Getting this wrong by 2× is the
most common first mistake.

| type | `size` means |
|---|---|
| `sphere` | radius |
| `box` | half-extents x, y, z |
| `capsule` | radius, half-length *excluding* the end caps |
| `cylinder` | radius, half-length |
| `ellipsoid` | three radii |
| `plane` | x/y **draw** extent, grid spacing — collision is infinite |
| `mesh` | taken from the mesh asset; see §8 |

Mass comes from one of three places, in order of precedence:
`mass="5"` (explicit kg) → `density="2700"` (kg/m³, times the volume) →
the default density of 1000 kg/m³ (water).

Prefer explicit `mass` when you know the real part's weight, and `density` when
you know the material. See `03_shapes.xml`, which uses all three.

## 5. Collisions

```bash
uv run python scripts/run.py scenes/02_collisions.xml
```

That scene shows three things at once: a **stack** of boxes settling (left),
a **bouncy vs dead** sphere pair (middle), and **slippery vs grippy** boxes on
a ramp (right), plus a **ghost** sphere that falls straight through the floor.

### Friction

```xml
<geom ... friction="1.0 0.005 0.0001"/>   <!-- sliding, torsional, rolling -->
```

Only the first number matters at the default `condim="3"`. MuJoCo's default is
`1.0`, which is quite grippy.

> **The rule that catches everyone:** the friction used for a contact is the
> **elementwise maximum** of the two geoms' values — not the average, not the
> minimum. A pair is slippery only if **both** geoms are slippery. One icy box
> on a grippy ramp still grips.

A box on a ramp slides when `friction < tan(tilt)`. The ramp in the scene is
tilted 20°, so `tan(20°) = 0.364`, and with the ramp itself at `0.05`:

| box | effective friction | result |
|---|---|---|
| slippery `0.05` | `max(0.05, 0.05) = 0.05` | slides off (travels 1.37 m) |
| grippy `1.00` | `max(0.05, 1.00) = 1.00` | holds (moves 0.04 m) |

Raise the ramp to `0.4` and the "slippery" box stops sliding even though you
never touched the box — that is the max rule biting.

### Bounce — `solref`

MuJoCo has no "restitution" or "bounciness" attribute. Contacts are **soft
constraints**, tuned with `solref`:

```xml
<geom ... solref="0.01 0.2"/>   <!-- timeconst, dampratio -->
```

- **`timeconst`** — how fast the contact responds, in seconds. Keep it at
  roughly 2× your timestep or larger, or contacts go unstable.
- **`dampratio`** — `1.0` is critically damped, i.e. **no bounce**. Below `1.0`
  is underdamped, i.e. **bouncy**. `0.2` is quite lively.

### `condim` — what kinds of friction exist

| `condim` | behaviour |
|---|---|
| 1 | frictionless — slides freely, like ice |
| 3 | **default** — adds tangential friction, so things slide and stop |
| 4 | adds torsional friction — resists spinning in place |
| 6 | adds rolling friction — balls eventually come to rest |

Use 3 unless you specifically need rolling to damp out; higher is costlier and
can be less stable.

### Turning collisions off — `contype` / `conaffinity`

Two geoms are tested for contact only when this bitmask test passes:

```
(contype_A & conaffinity_B) || (contype_B & conaffinity_A)
```

Setting both to `0` removes a geom from collision detection entirely while
still drawing it — the purple "ghost" sphere in the scene has mass and a
freejoint, so it falls, but it passes straight through the floor. This same
mechanism is how you stop two specific parts of a linkage from colliding.

### Seeing contacts

```bash
uv run python scripts/inspect_model.py scenes/02_collisions.xml --settle 3
```

```
  active contacts: 22

  geom A             geom B              penetration  normal force
  ------------------ ------------------ ------------ -------------
  floor              g_box_bottom           -0.294mm        58.86N
  g_box_bottom       g_box_middle           -0.367mm        39.24N
  ...
```

Negative penetration means the geoms overlap slightly. **That is normal** — soft
contacts must interpenetrate a little to generate force. A fraction of a
millimetre under load is healthy; millimetres of sink means the timestep is too
large or the masses are badly conditioned.

## 6. The step loop in Python

The real loop, from `scripts/run.py`:

```python
model = mujoco.MjModel.from_xml_path("scenes/01_ball_drop.xml")
data  = mujoco.MjData(model)

with mujoco.viewer.launch_passive(model, data) as viewer:
    while viewer.is_running():
        mujoco.mj_step(model, data)     # advance by model.opt.timestep
        viewer.sync()                   # push new state to the window
```

### `mj_step` vs `mj_forward`

| | what it does |
|---|---|
| `mj_step(model, data)` | computes forces, solves contacts, **integrates** — `data.time` advances |
| `mj_forward(model, data)` | computes all derived quantities for the current state — `data.time` does **not** advance |

Use `mj_forward` after you write to `qpos`/`qvel` by hand, and before the first
render. A fresh `MjData` has uninitialized `xpos`, so **rendering before any
`mj_forward` or `mj_step` gives a black frame** — every geom is still stacked at
the origin. `run.py` calls `mj_forward` up front for exactly this reason.

### Reading state

Every one of these is a numpy view into live memory — read and write directly.

| field | meaning |
|---|---|
| `data.time` | sim time, seconds |
| `data.qpos` | generalized positions, length `nq` |
| `data.qvel` | generalized velocities, length `nv` |
| `data.xpos[body_id]` | body world position, computed |
| `data.ncon` | number of active contacts right now |
| `data.contact[i]` | contact `i`: `.geom1`, `.geom2`, `.dist`, `.frame` |
| `data.qfrc_applied` | user-applied generalized forces |

Look names up rather than hardcoding indices, which shift when you edit the XML:

```python
bid = mujoco.mj_name2id(model, mujoco.mjtObj.mjOBJ_BODY, "ball")
print(data.xpos[bid])
```

### Real-time pacing

Physics and rendering run at different rates on purpose. The timestep is 2 ms
(500 Hz), but no screen needs 500 fps — and syncing the window that often is
slow enough to drag the sim below real time. So `run.py` steps physics as often
as the wall clock demands and syncs at ~60 Hz:

```python
wall   = time.perf_counter() - wall_start
target = sim_start + wall * speed
budget = 0
while data.time < target and budget < 200:   # cap avoids a catch-up spiral
    mujoco.mj_step(model, data)
    budget += 1
if wall >= next_sync:
    viewer.sync()
    next_sync = wall + 1/60
```

Without that split this project ran at 0.65× real time; with it, 1.00×.

### Two viewer flavours

| | behaviour |
|---|---|
| `viewer.launch_passive(model, data)` | **non-blocking** — your loop drives physics. Needs `sync()`. Used here. |
| `viewer.launch(model, data)` | **blocking** — runs its own loop. Simpler, but leaves nowhere for your code. |

(On macOS, `launch_passive` requires running under `mjpython` instead of
`python`. Not an issue on Linux.)

## 7. Changing the simulation

### In the XML

| to do this | change this |
|---|---|
| change gravity | `<option gravity="0 0 -1.62"/>` |
| make the sim more stable | halve `<option timestep="..."/>` |
| add an object | copy a `<body>` block, give it a new `name` and `pos` |
| make something heavier | `mass="5"` on its geom (or `density=`) |
| make something bouncier | `solref="0.01 0.2"` — lower the second number |
| make something slippery | `friction="0.05 ..."` on **both** geoms |
| pin a body in place | delete its `<freejoint/>` |
| stop two geoms colliding | `contype="0" conaffinity="0"` |
| start it moving | see `qvel` below — velocity is state, not XML |

### At runtime, in Python

```python
# teleport / set velocity. qpos layout for a freejoint:
#   [x, y, z, qw, qx, qy, qz]
data.qpos[0:3] = [0, 0, 5]        # move it to 5 m up
data.qvel[0:3] = [2.0, 0, 3.0]    # launch it
mujoco.mj_forward(model, data)    # REQUIRED after writing state by hand

# change gravity mid-flight - model.opt mirrors <option>
model.opt.gravity[2] = -1.62      # switch to the Moon, no recompile

# push on a body for one step
bid = mujoco.mj_name2id(model, mujoco.mjtObj.mjOBJ_BODY, "ball")
data.xfrc_applied[bid][2] = 200.0  # 200 N upward

# reset everything to the XML's initial state
mujoco.mj_resetData(model, data)
```

There is a marked `# --- poke the state here ---` block inside the loop in
`scripts/run.py` holding these same snippets, ready to uncomment.

### Building a scene from a string

Handy for quick experiments without a file:

## 8. Importing your own geometry

### Formats

| format | support |
|---|---|
| **STL (binary)** | yes — the usual CAD export |
| STL (ASCII) | **no** — convert it first |
| **OBJ** | yes |
| MSH | yes (MuJoCo's own binary mesh) |
| STEP, IGES, 3MF, FBX | **no** — convert to STL/OBJ first |

STEP is a CAD exchange format, not a mesh, so MuJoCo cannot read it. Your
`base_frame.py` already exports STL alongside STEP, which is the right move.

### Use the importer

```bash
uv run python scripts/import_mesh.py ../misc/pokeball.stl
```

It checks the three things that actually cause trouble, prints a paste-ready
MJCF snippet, and with `--write` emits a complete runnable scene:

```bash
uv run python scripts/import_mesh.py "../03 - Checks/base_frame.stl" \
    --name frame --drop-height 0.6 --write scenes/04_mesh_import.xml
uv run python scripts/run.py scenes/04_mesh_import.xml
```

### Gotcha 1 — units

**MuJoCo is strictly SI: metres, kilograms, seconds.** CAD exports millimetres.

Your `base_frame.stl` measures 490 × 490 × 350 in file units. Loaded as-is that
is a **490-metre** frame, and you would spend an afternoon wondering why it
falls in slow motion (it does not — it is just enormous, and a 490 m fall takes
10 s). The fix:

```xml
<mesh name="frame" file="base_frame.stl" scale="0.001 0.001 0.001"/>
```

`import_mesh.py` infers this from the bounding box: anything over 10 m across is
assumed to be millimetres, since nothing you simulate is genuinely that big.
Override with `--scale` if the guess is wrong.

### Gotcha 2 — mesh collision is the CONVEX HULL

This is the big one, and nothing warns you about it.

> A mesh geom collides as its **convex hull**. Pockets, vents, bores and open
> frames are invisible to collision — filled in solid.

On your base frame:

```
mesh volume 0.002191 m^3
hull volume 0.077502 m^3
mesh/hull   2.8%
```

The frame is 2.8% of its own hull. Visually it is an open box on legs; to the
physics it is a **solid block**. Nothing can pass between the legs or sit inside
it, and a bolt dropped into a hole bounces off a flat lid.

Two fixes, both standard:

**(a) Primitives for collision, mesh for looks.** The accurate and fast option.
Several geoms in one body are welded rigidly, share one freejoint, and never
collide with each other. Note that this mesh's origin is at its **base**
(z runs 0 → 0.35), not its center, so all the offsets below are measured up
from the foot plates.

The numbers come straight from the CAD source
(`assignment1/lunar-hopper/02-cad/base_frame.py`), converted mm → m — read them
off the named constants rather than eyeballing the STL:
`FOOT_PLATE` 90×90×10, `LEG_SECTION` 40, `LEG_HEIGHT` 300, `FRAME_SPAN` 400,
`BEAM` 50×50.

```xml
<body name="frame_body" pos="0 0 0.4">
  <freejoint/>

  <!-- visual only: drawn, never collides -->
  <geom type="mesh" mesh="frame" contype="0" conaffinity="0"
        rgba="0.7 0.7 0.75 1"/>

  <!-- foot plates: 90x90x10 under each leg, on the 400 mm span -->
  <geom type="box" size="0.045 0.045 0.005" pos="-0.2 -0.2 0.005"/>
  <geom type="box" size="0.045 0.045 0.005" pos=" 0.2 -0.2 0.005"/>
  <geom type="box" size="0.045 0.045 0.005" pos="-0.2  0.2 0.005"/>
  <geom type="box" size="0.045 0.045 0.005" pos=" 0.2  0.2 0.005"/>

  <!-- legs: 40x40 square, foot top (z=0.010) to beam underside (z=0.300) -->
  <geom type="box" size="0.02 0.02 0.145" pos="-0.2 -0.2 0.155"/>
  <geom type="box" size="0.02 0.02 0.145" pos=" 0.2 -0.2 0.155"/>
  <geom type="box" size="0.02 0.02 0.145" pos="-0.2  0.2 0.155"/>
  <geom type="box" size="0.02 0.02 0.145" pos=" 0.2  0.2 0.155"/>

  <!-- beams: 50x50 section, z = 0.300..0.350 -->
  <geom type="box" size="0.22  0.025 0.025" pos=" 0   -0.2  0.325"/>
  <geom type="box" size="0.22  0.025 0.025" pos=" 0    0.2  0.325"/>
  <geom type="box" size="0.025 0.22  0.025" pos="-0.2  0    0.325"/>
  <geom type="box" size="0.025 0.22  0.025" pos=" 0.2  0    0.325"/>
</body>
```

This is shipped as a runnable scene — **`scenes/05_mesh_collision_proxy.xml`**:

```bash
uv run python scripts/run.py scenes/05_mesh_collision_proxy.xml
```

It drops an orange ball down the middle as proof. Measured both ways:

| | ball ends at | meaning |
|---|---|---|
| `04_mesh_import.xml` (plain mesh) | z = **0.3995** | stopped on an invisible solid lid |
| `05_mesh_collision_proxy.xml` | z = **0.0496** | fell *through*, landed on the floor inside the legs |

0.0496 m is the ball's own radius, i.e. resting on the ground. The frame itself
settles to z = 0.0000 on 16 contacts — all four foot plates down, nothing else
touching. (Proxy mass comes out at 64.6 kg at the default density; set an
explicit `mass` if the real figure matters.)

The compound T-shape in `03_shapes.xml` is a worked example of this pattern.

**(b) Split the part into convex pieces** in CAD, export each as its own STL,
and add one mesh geom per piece in the same body. More faithful, more work.

### Gotcha 3 — watertightness

A mesh that is not watertight has no well-defined volume, so MuJoCo cannot
compute mass or inertia reliably. `import_mesh.py` reports this; set an explicit
`--mass` when it does.

### Where mesh paths resolve

Relative `file=` paths resolve against `<compiler meshdir="...">`, or the XML's
own directory if `meshdir` is unset. `import_mesh.py` writes absolute paths, so
generated scenes work from anywhere.

## 9. Troubleshooting

### 9.1 Integrators: Euler, RK4, and when to switch

The integrator determines how the solver advances state forward in time. It is
specified as `<option integrator="..."/>` and cannot be changed without
recompiling the model. Here is what each one does and when to use it:

#### **Euler (the default)**

The simplest method: one evaluation of the force function per timestep.

```
q[t + dt] = q[t] + dt · qvel[t]
qvel[t + dt] = qvel[t] + dt · acceleration[t]
```

**Pros:**
- Fast — one force evaluation per step
- Works well with **contacts**, which the Euler solver is tuned for
- Stable with small timesteps

**Cons:**
- First-order accurate — error grows linearly with timestep size
- Energy drifts; a ball bouncing in vacuum will gain or lose height
- Bad on **smooth stiff dynamics** (springs, dampers, gyro stabilization) where
  the timestep must be very small to stay stable

Use Euler if:
- You have many contacts (the default scenes here all use it)
- Your timestep is already small (2 ms = 500 Hz is standard)
- Things are not exploding or sinking

#### **RK4 (Runge-Kutta 4th order)**

Four force evaluations per step, advancing in substeps to fit the arc of motion.

```
k1 = acceleration[t]
k2 = acceleration[t + 0.5·dt with state at midpoint using k1]
k3 = acceleration[t + 0.5·dt with state at midpoint using k2]
k4 = acceleration[t + dt with state at endpoint using k3]
advance using a weighted average: (k1 + 2·k2 + 2·k3 + k4) / 6
```

**Pros:**
- 4th-order accurate — much smaller error per unit timestep
- Conserves energy better; bouncing ball holds altitude
- Handles **smooth dynamics** (springs, dampers, gyro) well; you can use a
  larger timestep and still be stable

**Cons:**
- 4× more expensive per step (four force evals instead of one)
- Contacts are not special — each substep uses the same solver
- Can be less stable with hard contacts if you push the timestep too far

Use RK4 if:
- Your vehicle has spring dampers or gyros (the mission brief does not, but a
  real cubesat would)
- You have smooth dynamics and energy conservation matters
- You are tired of halving the timestep and watching it get no better

#### **implicitfast**

A semi-implicit method tuned for damping-heavy systems.

**Pros:**
- Handles strong damping without exploding
- Good energy conservation

**Cons:**
- Slower than Euler
- Rarely needed for this project

Use `implicitfast` only if you add very strong damping (like landing gear shock
absorbers) and the simulation becomes unstable.

#### **How to diagnose which integrator you need**

1. **Start with Euler at 2 ms (500 Hz).** It is the default and works for
   contacts.
2. **If things explode, jitter, or sink** → halve the timestep to 1 ms first.
   Euler is first-order, so doubling the frequency does much more than you might
   expect.
3. **If the smaller timestep helps but you are not happy with CPU cost** →
   switch to RK4 and try 2 ms or even 4 ms. Each of the four substeps sees the
   half-sized effective timestep, giving you accuracy closer to 0.5 ms under
   Euler.
4. **If you add springs or gyro dampers and it becomes unstable** → try RK4
   first, then `implicitfast`.

#### **A practical example from this project**

The thruster scenes use Euler at 2 ms. The dynamics are smooth (no springs) and
the main loops are feedforward thrust + a simple PD controller (integrating
nothing; just proportional + derivative), so energy drift is not an issue and
contacts are rare. RK4 would buy almost nothing here; switching to it would use
4× the CPU for identical results.

If we added a spring-mounted gimbal (the main engine on a 3-DOF ball joint with
damped springs) the story would change. A stiff spring would couple to the 2 ms
timestep, causing oscillation. RK4 with 4 ms (giving an effective 1 ms resolution
across its substeps) would stabilize it while cutting CPU cost vs Euler at 0.5
ms.

```

### The viewer will not open

```

`MUJOCO_GL` selects the backend and **must be set before `import mujoco`** —
MuJoCo links its GL backend at import time, so setting it afterwards does
nothing. This is why the import in `run.py` sits inside `main()` rather than at
the top of the file.

| value | use |
|---|---|
| `glfw` | on-screen window. Works via WSLg here. |
| `egl` | headless, GPU. The default for `--headless`. |
| `osmesa` | headless, pure software. Slow, but works anywhere. |

On WSL2 this machine renders through `llvmpipe` (software), which is fine for

### Renders come out black

Call `mj_forward` (or step) before rendering, and `update_scene` before each
frame. A fresh `MjData` has every body at the origin until something computes
`xpos`.

### `Image width 1280 > framebuffer width 640`

MuJoCo's offscreen framebuffer defaults to 640×480. Raise it in the XML:

```xml
<visual>
  <global offwidth="1280" offheight="720"/>
</visual>
```

All the scenes here already do.

### Objects fall through the floor, jitter, sink, or explode

In order: halve `timestep`; avoid very thin geoms (a plate as a thin box is
worse than a box with real thickness); check for absurd mass ratios — a 1000:1
mass ratio in one contact is hard on any solver; raise `<option iterations>`.
A thing moving more than its own smallest dimension in one timestep can tunnel
through a wall before the contact is ever detected.

### A script is named after a stdlib module

Worth knowing, since it bit this project: a script in `scripts/` named
`inspect.py` shadows Python's stdlib `inspect`, because the script's own
directory goes on `sys.path` first. numpy then imports *your* file and dies with
a confusing circular-import error. That is why the tool here is
`inspect_model.py`. Avoid naming files `inspect.py`, `types.py`, `json.py`,
`random.py`, and friends.

## 10. Forces and thrust

Everything above is passive: gravity and contacts. This section is about making
the vehicle *push* — thrust vectors you can steer and throttle from a control
law that reads the current state.

```bash
# the example controller holding altitude, with visible thrust vectors
uv run python scripts/fly.py scenes/06_thrust_craft.xml \
    --controller example_hover:hover --arrows --camera chase

# prove the physics is right (50 numeric checks)
uv run python scripts/fly.py --selftest
```

### Three ways to apply force, and which to use

| mechanism | frame | what it is good for |
|---|---|---|
| `<general>` actuator on a `<site>` | **body** | **thrusters.** Rides the body, clamped to a range, steerable. |
| `data.xfrc_applied[body]` | world | one-off pushes, wind, tether loads. You do the rotation yourself. |
| `data.qfrc_applied` | joint | torques straight into a joint's DOF. |

A thruster wants the first one. The force direction is stored in the body frame,
so the engine keeps pointing "down the craft's axis" however the vehicle tumbles
— no bookkeeping from you. `xfrc_applied` is world-frame, so you would have to
rotate the vector yourself every step and it would silently keep pushing in a
fixed world direction while the craft rotated.

### The mechanism

Two XML elements. A `<site>` says **where** the force acts; a `<general>`
actuator bound to it says **what** force:

```xml
<site name="noz_main" pos="0 0 -0.25"/>
<general name="thr_main" site="noz_main" gear="0 0 1 0 0 0" ctrlrange="0 60"/>
```

`gear` is `"Fx Fy Fz Tx Ty Tz"` in the site frame — first three force, last three
torque. The split that makes control possible:

```
data.ctrl[i]                 ->  MAGNITUDE, Newtons
model.actuator_gear[i][:3]   ->  DIRECTION, unit vector in the site frame
```

Both are writable every step. Writing `ctrl` throttles; writing `gear` **steers**.
That is thrust vectoring, and it is the whole trick.

### ⚠ The trap: `gear` scales the force

`gear` does not merely aim the force — it multiplies it. Measured:

| `gear` | `ctrl` | resulting thrust |
|---|---|---|
| `[0, 0, 1]` | 10 | 10.0 N ✓ |
| `[0, 0, 2]` | 10 | **20.0 N** ✗ |
| `[1, 1, 1]` | 10 | **17.32 N** (= 10·√3) ✗ |

So a direction vector **must be normalized**, or your commanded Newtons are not
the Newtons you get — and nothing warns you. `Thruster.set()` normalizes every
direction it is given, which is most of why the wrapper exists. If you write
`actuator_gear` by hand, normalize it yourself.

Two related behaviours worth knowing:

- **`ctrlrange` is enforced by MuJoCo.** `ctrl=999` on a `0 60` actuator applies
  60 N; `ctrl=-5` applies 0. The lower bound is 0 because a rocket cannot pull.
  `Thruster.set()` also clamps, so the value you *log* is the value applied.
- **Offset thrust makes torque.** A site displaced from the centre of mass
  produces a moment `r × F`. Measured: a site 0.1 m off-axis firing 10 N gives
  1.0 N·m. This is why attitude control exists.

### The API

`scripts/thrusters.py`. Thrusters are discovered from the model by scanning for
site actuators with the `thr_` prefix, so adding one to the XML is all it takes
— there is no index table to maintain.

```python
from thrusters import ThrusterSet, CraftState

thr = ThrusterSet(model)
thr.names                                  # ['main', 'rcs_px', ...]

thr["main"].set(model, data, 19.44)                      # magnitude only
thr["main"].set(model, data, 25.0, [0.1, 0, 1])          # + direction (normalized)
thr["main"].set_throttle(model, data, 0.5)               # 0..1 of max, like the
                                                         #   firmware's setPower()
thr["main"].gimbal(model, data, 25.0, pitch_deg=12)      # aim by angle
thr["main"].off(data)

thr["main"].force_world(model, data)       # current force, world frame
thr.total_force_world(data)                # vector sum of all thrusters
thr.apply(data, {"main": (25.0, [0, 0, 1]), "rcs_px": 4.0})
```

`CraftState` is the snapshot handed to your control law:

| field | frame | meaning |
|---|---|---|
| `t` | — | sim time, s |
| `pos` | world | position |
| `vel` | **world** | linear velocity |
| `quat` | — | orientation, `[w,x,y,z]` |
| `angvel` | **body** | angular velocity — what a rate gyro reads |
| `euler_deg` | — | roll/pitch/yaw, degrees, for reading |
| `up` | world | the craft's thrust axis; `[0,0,1]` when upright |
| `mass`, `gravity` | — | `weight_n()` gives `m·g`, `tilt_deg()` the tilt |

**Frames here are genuinely easy to get wrong, so they are worth stating.** For a
freejoint, `data.qvel[3:6]` is **body**-frame angular velocity while
`data.cvel[bid][:3]` is **world**-frame. Rotating `cvel` by the body quaternion
therefore rotates an already-world vector a second time — which reads correctly
while the craft is upright and silently wrong the moment it tilts. `CraftState`
uses `mj_objectVelocity` with the explicit `flg_local` argument instead, and the
self-test pins both conventions.

### The control loop

```python
state = CraftState.from_data(model, data, body_id)   # 1. what is it doing?
cmds  = controller(state)                            # 2. what should it do?
thrusters.apply(data, cmds)                          # 3. write ctrl + gear
mujoco.mj_step(model, data)                          # 4. integrate
```

Commands persist in `data.ctrl` and `model.actuator_gear` until overwritten, so a
thruster keeps firing between ticks — a zero-order hold, which is what real
hardware does too.

A control law is just a function:

```python
def hover(state):
    err_alt = TARGET_ALT_M - state.pos[2]
    thrust = state.weight_n() + KP_ALT * err_alt + KD_ALT * (-state.vel[2])
    return {"main": (thrust, [0.0, 0.0, 1.0])}
```

Return `{name: magnitude}` or `{name: (magnitude, direction)}`. Thrusters you do
not mention are left alone. Run it with `--controller module:function`.

Two notes on timing. `--control-hz 50` runs the law at 50 Hz instead of every
physics step, which is more honest — a real flight computer cannot correct a
500 Hz disturbance. And if you use the `RK4` integrator and want the law
evaluated at substeps too, register it with `mujoco.set_mjcb_control` instead of
calling it from your own loop.

### Changing the setpoint while it flies

`hover` reads the `TARGET_ALT_M` constant, so retargeting means editing the file
and restarting. `hover_interactive` is the same law reading a live variable that
a background thread updates from the terminal:

```bash
uv run python scripts/fly.py scenes/06_thrust_craft.xml \
    --controller example_hover:hover_interactive --duration 60
```

Then type, and press Enter:

| typed | effect |
|---|---|
| `3.5` | absolute target, 3.5 m |
| `+0.5` / `-1` | relative to the current target |
| `+` / `-` | nudge by `ALT_STEP_M` (0.5 m) |
| `?` | report the current target |

Targets outside `ALT_MIN_M`-`ALT_MAX_M` (0.3-15 m) are clamped *and* announced,
so a refused number is visible rather than silently ignored.

The listener starts lazily on the first control tick, not at import, because
`selftest_thrust.py` imports this module and `--selftest` must not compete for
stdin. With no TTY (`--headless`, `--video`, piped input) no thread is started
and the target stays at its default — a reader looping on a closed stdin would
spin.

**What this makes visible.** The gains were tuned for holding an altitude, not
for stepping it. Measured, from a settled hover:

| step | overshoot | actuator saturated |
|---|---|---|
| 2 → 3 m | 0.029 m | never |
| 3 → 12 m | **1.193 m** | 60 N for 1.12 s |

A 9 m error asks `KP_ALT` for 162 N from a 60 N engine. While the command is
pinned at the limit the loop is effectively open, and the D term only begins
arresting the climb once the error has shrunk enough to come out of saturation.
That is standard PD-against-a-saturating-actuator behaviour, and the fix is to
ramp the setpoint — fly a trajectory — rather than step it.

### Seeing the vectors

`--arrows` draws one arrow per firing thruster, starting at the nozzle and
pointing **opposite** the force — i.e. where the exhaust goes. Length scales with
*throttle fraction*, not absolute Newtons, so a 20 N RCS jet and a 60 N main
engine are both visible in one frame.

Use `--camera chase` with it. The default free camera zooms out to fit the whole
world, which shrinks the arrows to nothing; the `chase` camera in
`06_thrust_craft.xml` rides the craft at its own height so the plumes read
side-on instead of foreshortening to a dot.

### What the example scene teaches

`scenes/06_thrust_craft.xml` is a 12 kg craft with a 60 N steerable main engine
at `X=Y=0` on the base, plus a four-jet RCS quad 0.25 m above the centre of mass
firing sideways. Building it surfaced two design lessons that are worth more than
the code:

**1. Attitude authority is a sizing calculation, not a tuning problem.** The RCS
started at 5 N each — 5 N × 0.25 m = 1.25 N·m. A canted main engine 0.25 m below
the centre of mass produces up to 3.6 N·m against it at hover throttle. The
attitude loop therefore *lost*: position converged beautifully to x = 1.003,
z = 2.000 while the craft hung **upside down** at 179.9° tilt, which is a
perfectly stable equilibrium. No gain retune fixes an under-actuated vehicle. The
jets are 20 N (5.0 N·m) and the cant is capped at ~12°, giving a measured 1.55×
margin over the worst case, and the self-test asserts that margin.

**2. Nozzle orientation matters.** The RCS jets originally all fired `+Z` like
the main engine, so every attitude correction also shoved the craft upward by
5 N, fighting the altitude loop. Each `<site>` now carries a `euler` that aims
its thrust horizontally, giving near-pure torque — verified at 20 N horizontal
force, 5.0 N·m torque, **0.0 N** of parasitic lift.

Also note the inverted-equilibrium subtlety in `example_hover.py`: `state.up`'s
x/y components are a convenient tilt error, but they vanish at *both* 0° and
180°, so a naive law sees zero error while hanging upside down.

### Debugging thrust

```bash
uv run python scripts/fly.py --selftest           # 50 numeric checks
uv run python scripts/inspect_model.py scenes/06_thrust_craft.xml
```

| symptom | likely cause |
|---|---|
| nothing moves | missing `<freejoint/>`, or `ctrl` is 0 |
| thrust is the wrong size | un-normalized direction — `gear` scales force |
| craft tumbles | offset thrust makes torque; you need attitude control |
| craft flips and stays flipped | 180° is a stable equilibrium for a naive tilt error |
| attitude loop loses | thruster torque < disturbance torque; resize, do not retune |
| wrong direction once tilted | world-frame vector written as body-frame `gear` |
| works upright, fails tilted | a frame error that only shows up off-vertical |
| `no thrusters` error | actuator is not a site actuator, or lacks the `thr_` prefix |

### Logging, for comparing against the bench

`--log out/flight.csv` writes `time_s`, one column of Newtons per thruster, then
position, velocity and attitude. The schema deliberately mirrors the course's
load-cell firmware (`millis,raw,counts,force_N`) so a simulated thrust curve can
be diffed against a measured one.

## 11. A standardized test scenario

Comparing two control laws by watching numbers scroll past does not work. This
runs any controller through one fixed profile and writes the plots and metrics
to a timestamped directory, so two runs can be put side by side.

```bash
uv run python scripts/scenario.py --controller example_hover:hover
uv run python scripts/scenario.py --controller example_hover:hover --target 3.5
uv run python scripts/scenario.py --selftest        # 19 numeric checks
```

### The profile

| phase | setpoint | ends when |
|---|---|---|
| `GROUND_SIT` | the resting height | 2 s elapse |
| `ASCEND` | **steps** to the target | craft arrives *and* has settled |
| `HOLD_TARGET` | the target | 5 s elapse |
| `DESCEND` | **ramps** down at `DESCENT_RATE_MPS` | setpoint reaches the floor and the craft settles |
| `GROUND_HOLD` | the resting height | 3 s elapse |

The hold clocks start on **arrival**, not when the setpoint changes, so a slow
controller still gets a full 5 s genuinely at altitude. Arrival requires both
`|z - goal| < 0.05 m` **and** `|vz| < 0.05 m/s` — position alone fires too
early, since `hover` enters the band at t=2.67 s while still climbing toward a
2.05 m overshoot. Any phase that never arrives times out (30 s, plus the ramp
time for the descent) and records the fact rather than hanging.

### Why a descent *rate* works on a position-only law

None of these controllers takes a velocity command. The scenario does not give
one — it **ramps the position setpoint** and lets the law chase it. Measured on
`07_thrust_1D`, descending from 2.0 m:

| commanded | peak descent speed | time to ground |
|---|---|---|
| stepped setpoint | −0.863 m/s | 2.95 s |
| ramp 0.1 m/s | **−0.103 m/s** | 17.63 s |
| ramp 0.5 m/s | −0.508 m/s | 5.20 s |

So the rate is real and no control law had to change. At the 0.1 m/s default the
descent alone takes ~16 s, making a full run ~31 s.

**What this exposes.** A P+D law cannot track a ramp without a steady offset. At
constant descent the acceleration is zero, so `KP·e + KD·rate = 0`, giving
`e = −KD·rate/KP`. With the example gains that predicts **−0.1222 m** and
measures **−0.1218 m** — the lag is visible in the altitude panel as the blue
trace riding below the dashed setpoint all the way down. This is exactly the
steady-state error an integral term removes, so `descent_lag_mean_m` is the
metric to watch when comparing a PD law against a PID one.

### Making a controller drivable

Each law keeps its setpoint wherever it chose to, so the scenario needs one
uniform way in. Define `set_target(alt_m)` in your controller's module:

```python
def set_target(alt_m):
    global TARGET_ALT_M
    TARGET_ALT_M = float(alt_m)
```

Without it the runner refuses the controller and prints that snippet rather
than flying a law it cannot command. `example_hover.set_target` sets both
`TARGET_ALT_M` and `_target_alt`, which is why all three laws there work.

### What a run writes

```
outputs/<scene>_<controller>_<YYYY-MM-DD_HHMMSS>/
    flight.csv    every tick: setpoint, pos, vel, both accelerations,
                  applied thrust per thruster, raw command per actuator, phase
    flight.png    five stacked panels, phases shaded
    run.json      profile constants, phase boundaries, metrics, timeouts
    summary.txt   the same metrics, readable
```

`outputs/` is gitignored. The CSV keeps **both** applied thrust (`main_N`) and
raw command (`ctrl_main`) because they differ whenever the actuator saturates —
that difference *is* the saturation. It also keeps two acceleration columns, one
differenced from velocity and one read from the solver's `qacc`; measured they
agree to 6e-05 m/s², but keeping both makes a disagreement visible rather than
silent if the timestep grows or the control rate is decimated.

The ground height is **derived**, not hardcoded: `07_thrust_1D`'s capsule rests
with its origin at 0.399928 m, `06_thrust_craft`'s box at 0.249977 m. The run
starts already resting there, since letting the craft drop would inject a
0.57 m/s impact into the middle of the first phase.

## 12. Where to go next

This project deliberately covers only gravity and collisions. The natural next
steps, and where each attaches:

- **Joint actuators** — §10 covers site actuators (thrusters). The other kind
  drives a joint: `<actuator><motor joint="..."/></actuator>`, also via
  `data.ctrl`. That is how you build a gimbal that physically rotates, rather
  than steering by rewriting `gear`.
- **Cold-gas blowdown** — the course's real propulsion is a nitrogen bottle whose
  pressure *falls* over a 10-20 s burn, and the mission brief calls modelling
  that "the part your model has to get right". Thrust is currently constant for a
  given command; make `max_thrust_n` fall with tank state and the control problem
  gets considerably more interesting.
- **Solenoid bang-bang** — the real valve is open/closed with ~6 ms enable and
  ~2 ms disable transients, commanded as a 0-1 duty cycle, not a continuous
  force. `Thruster.set_throttle()` already takes that 0-1 convention, which is
  where a duty-cycle model would attach.
- **Fuel depletion** — propellant mass leaving the vehicle changes `body_mass`
  and the inertia tensor mid-flight.
- **Joints other than free** — `<joint type="hinge"/>`, `slide`, `ball`, with
  `range`, `stiffness` and `damping`. Chain bodies to build a linkage.
- **Sensors** — `<sensor>` with `accelerometer`, `gyro`, `force`, `framepos`.
  Values appear in `data.sensordata`. The obvious bridge to GNC work.
- **Fixed cameras** — `<camera name="..." pos="..."/>`, then
  `renderer.update_scene(data, camera="name")` for repeatable views.
- **Equality constraints** — `<equality>` to weld or connect bodies.
- **Keyframes** — `<keyframe><key qpos="..."/></keyframe>` plus
  `mj_resetDataKeyframe` for reproducible initial conditions.
